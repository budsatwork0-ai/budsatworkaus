# Migration baseline investigation

## Finding

The repository currently has an upgrade chain, not a reproducible fresh-database chain. A formal schema-only baseline is required before an empty database can be supported safely.

## Evidence

- Commit `a5d3972e4a378dc1387c72602646af86b84f4284` (“Migration history reconciliation — timestamp-prefix all migration files”) moved 65 pre-tracking files into `supabase/migrations/legacy/`, created 11 empty stubs for remote-only history, and stated that the goal was a clean `supabase db push --linked` against the existing deployed history.
- The normal top-level chain applies `001_orders_subscriptions.sql` and `20260416004709_023_payouts.sql`, then fails in `20260416040239_024_security_cleanup.sql` because `public.employees` is absent.
- `legacy/006_employee_crew.sql` creates `employees`, `job_assignments`, and `job_completions`, explaining the immediate missing dependency.
- The historical files cannot safely be restored as a bootstrap chain: migration 006 creates `employees.user_id`, while migration 007 unconditionally alters and renames `employees.clerk_user_id`.
- `legacy/combined_migration.sql` overlaps the numbered core migrations and identifies itself as a one-file SQL Editor migration, not a migration-runner version.
- Eleven timestamped top-level files explicitly state that their SQL was applied directly and was unavailable when history was reconciled. Replaying local historical SQL therefore cannot reproduce the authoritative deployed schema.
- No `supabase/config.toml`, schema dump, supported bootstrap script, or CI fresh-install job exists in the repository.
- `src/types/database.ts` is useful application evidence but explicitly says types “should be regenerated”; it is not a schema dump and omits database policies, grants, triggers, and complete constraint definitions.

## Authoritative model

The evidenced model is a combination of model C and D:

1. Existing deployments are expected to contain a pre-existing schema and reconciled migration history.
2. The top-level timestamped files are authoritative only for upgrades from that state.
3. Historical SQL is incomplete and internally inconsistent for empty-database replay.
4. A new, reviewed schema-only baseline is required for fresh installations.

## Safe next step

Capture a schema-only dump from an authorised disposable clone of the deployed schema, or from another reviewed authoritative database artifact supplied by the owner. Do not use production credentials during automated validation. Review the dump for data, credentials, ownership, extension availability, RLS, grants, function security, and `search_path`; adopt it as a versioned baseline only after comparison with application calls and generated types.

The exact owner handoff, export scope, provenance metadata, and secure-delivery requirements are defined in `authoritative-baseline-artifact-request.md`.

Existing deployments must continue using the current timestamped upgrade chain. A fresh-install runner must apply the future baseline first and only the explicitly declared post-baseline tail afterward; it must never replay the legacy directory or falsify migration history.

The structured per-file inventory is in `migration-inventory.json` and is regenerated by `scripts/migration-inventory.mjs`.
